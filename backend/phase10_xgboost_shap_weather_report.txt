# PHASE 10: XGBOOST + SHAP + WEATHER INTEGRATION REPORT

## 1. Architecture Audit
Before implementation, the architecture was audited. The pipeline was confirmed to strictly use HTML/CSS/Vanilla JavaScript, FastAPI, YOLOv11, and PostgreSQL. `xgboost` and `shap` were verified in `requirements.txt`.

## 2. Feature Engineering
Numerical features were extracted from the YOLO detections and the weather context to feed into the XGBoost model. 
Features engineered:
- `detection_count`: Total number of detected objects
- `max_confidence`: Maximum confidence score among detections
- `mean_confidence`: Average confidence score
- `class_0_count`, `class_1_count`: Number of objects belonging to each class
- `largest_bbox_area_ratio`: Proportion of the image area taken up by the largest detected bounding box
- `total_detected_area_ratio`: Proportion of the image area covered by all detections combined
- Contextual Features: `temperature`, `humidity`, `wind_speed`, `precipitation`

## 3. Rule-Derived Label Methodology
The dataset labels are NOT scientifically validated for true geological rockfall occurrence. Therefore, an explicit heuristic rule was created to assign **experimental risk labels** (LOW, MEDIUM, HIGH) to the extracted feature vectors:
- **HIGH**: If `detection_count >= 5`, OR `max_confidence > 0.8`, OR `precipitation > 10`
- **MEDIUM**: If `detection_count >= 2`, OR `max_confidence > 0.5`
- **LOW**: Otherwise

## 4. XGBoost Training
A synthetic dataset was generated by passing the 462 validation images through the YOLOv11 model, extracting features, and applying the experimental labels.
- **Model**: `XGBClassifier(n_estimators=100, max_depth=4, learning_rate=0.1, random_state=42)`
- **Output**: `backend/models/risk_xgboost.json`

## 5. Real Evaluation Metrics
Because the XGBoost model was trained on the explicitly rule-derived dataset, it perfectly learned the injected heuristics:
- **Accuracy**: 1.000 (100%)
- **Precision**: 1.000 (100%)
- **Recall**: 1.000 (100%)
- **F1-Score**: 1.000 (100%)
*Note: These metrics strictly measure the model's ability to replicate the programmatic heuristic rule, NOT real-world predictive validity.*

## 6. SHAP Implementation
`shap.TreeExplainer` was integrated into the `assess_risk()` pipeline. For each prediction, SHAP calculates the exact contribution values of each feature to the final risk classification. The frontend displays the Top 4 contributing features and their specific values.

## 7. Weather API Implementation
A backend endpoint `GET /api/weather` was created to interface securely with OpenWeatherMap.
- Retrieves: Temperature, Humidity, Wind Speed, Weather Condition, and Rain.
- Securely pulls `OPENWEATHERMAP_API_KEY` from `.env`.
- Handles failure cases gracefully by returning appropriate error messages.

## 8. Browser Geolocation
The Vanilla JavaScript frontend natively requests geolocation permissions via `navigator.geolocation`. If approved, coordinates are dynamically piped into the backend `/api/weather` endpoint. If denied, it defaults to a polite "Location permission required" notice.

## 9. PostgreSQL Changes
The `PredictionHistory` table was dynamically extended (via an `ALTER TABLE` schema migration script) to support the new metadata:
- `risk_status` (LOW/MEDIUM/HIGH/NOT_AVAILABLE)
- `experimental_flag` ("True")
- `features_json`
- `shap_json`
- `weather_json`

## 10. API Endpoints
- **GET /api/weather**: Returns real-time JSON weather data based on lat/lon coordinates.
- **POST /api/predict**: Extended to accept `weather_data` inside `FormData`. Processes YOLO, then runs XGBoost/SHAP on the result.
- **GET /api/simulate**: Extended to accept `weather_data` as a query parameter. Processes the same end-to-end flow.

## 11. Frontend Changes
- **Dashboard**: Weather monitoring card displays live OpenWeatherMap data.
- **Predictions / Simulation**: The result card UI was significantly upgraded to display an "EXPERIMENTAL RISK ASSESSMENT" sidebar detailing the Risk Level, XGBoost validation warnings, and the SHAP explainability breakdowns.
- **Model Performance**: Added a dedicated section detailing the experimental XGBoost metrics.

## 12. End-to-End Tests
All modules verified: YOLO extraction works, OpenWeatherMap gracefully handles missing API keys, SHAP computes correctly, UI elegantly integrates the full feature cascade, and PostgreSQL successfully logs the extended schema payload.

## 13. Limitations
The weather API heavily relies on the user providing their own API key. Also, since SHAP requires valid model outputs, any failure in XGBoost initialization results in graceful failure of the explainability rendering.

## 14. Scientific Validation Limitations
**CRITICAL:** As established, ROCKGUARD AI does **NOT** scientifically predict future rockfall events.
The current system is defined entirely as: *"YOLOv11-based mine-image object detection with an experimental XGBoost risk-assessment layer, SHAP-based explanation, and real-time weather context."* No probabilistic forecasting is occurring.
